# 技术方案评审

技术方案有两类高成本错误，本 skill 都管：

1. **数据错误** —— 代码写错可以改，表设计错、字段语义错、迁移方向错，上线后修复成本呈数量级上升。
2. **看不懂** —— 方案的读者是人：评审的同事、几个月后接手的开发、跨端对接方、以及未来的自己。写成只有作者自己看得懂的行话，读者要么读不懂，要么**假装读懂了** —— 后者更危险，因为评审会走过场，问题留到上线才炸。

评审按维度组织。用户明确说「只看数据」或「只看写得清不清楚」时可只跑其中一维，默认全跑。Gate 0 任何情况下都不可跳过。

## Gate 0：基线感知核查（不通过直接打回，不进后续清单）

**方案作者最常见、代价最大的失败不是设计错，而是基于过期基线调研，把已经上线的能力当成不存在，去重复实现或重复建表。** 这一关必须先过。

典型症状：作者在 `uat` / `dev` / 旧 feature 分支上 grep，那个 checkout 落后 `origin/main` 几百个 commit，于是得出「仓库里没有 X 能力」「这张表不存在」，方案里写了一套全新实现，而 `origin/main` 上早就有了。

### 0.1 先量偏离度

```bash
git status --short --branch
git fetch --prune
git log -1 --format="%h %ad %s" --date=short origin/main
git rev-list --left-right --count HEAD...origin/main   # 左=本地独有 右=落后
```

对多仓需求，每个涉及的仓库都跑一遍。

| 落后 commit 数 | 处置 |
|---|---|
| 0 | 基线新，继续 |
| 1–20 | 继续，但方案里所有否定结论仍需在 `origin/main` 复核 |
| > 20 | **默认判定基线不可信**。方案里每一条「现状」和「不存在」断言都必须逐条在 `origin/main` 上重新验证后才能进入数据评审 |

### 0.2 检查方案是否标注了基线

- [ ] 方案文档写明基线 commit hash + 日期，且该 commit 属于 `origin/<默认分支>`
- [ ] 没写基线，或基线是本地分支 / 工作区 → **打回**，要求作者补齐后重新提交
- [ ] 标注的 commit 与当前 `origin/main` 差距过大（> 20 commit 或 > 1 周）→ 要求作者在最新基线上复核

### 0.3 逐条复核否定结论（最关键一步）

把方案里所有形如「现在没有 X」「需要新建 Y」「缺少 Z 能力」的断言提取出来，**每一条**在 `origin/main` 上独立验证：

```bash
# 代码能力是否已存在
git grep -niE "<关键词1|关键词2|同义词>" origin/main -- "*.go" "*.proto" "*.api"

# 文件是否已存在（别只搜关键词，也按路径/文件名找）
git ls-tree -r --name-only origin/main | grep -iE "<pattern>"

# 读实现，不读工作区
git show origin/main:path/to/file.go

# 表/字段是否已存在：在 migration 仓同样带 revision 搜
git grep -niE "create table .*<table>|alter table .*<table>|<column_name>" origin/main
```

搜索要求：

- **换多组关键词**。搜不到不等于不存在。同一能力可能叫 `transcription` / `speech_to_text` / `asr` / vendor 名（`deepgram` / `whisper`）。至少试 3 组同义词和 2 种命名风格（snake / camel）。
- **搜实体不只搜动作**：表名、字段名、proto message、RPC 方法名、配置 key 都试。
- **反向验证**：找到疑似已有实现时，读它的完整实现和调用方，确认它是否真的覆盖本次需求，而不是名字像。
- 复核结果逐条记录：断言 → 验证命令 → 结论（成立 / 不成立 / 部分成立）。

**特别注意「会上口头结论」类断言。** 方案里凡是写「据了解已经 X」「应该已经收敛到 Y」「听说是 by Z 配的」，一律按未验证处理并逐条核实 —— 口头判断的错误率显著高于代码事实，且一旦写进方案就会被当成既定前提，后续所有设计都建在上面。

### 0.4 检查是否漏掉已有可复用资产

- [ ] `origin/main` 上是否已有同类表 / 字段，本次是否在重复建
- [ ] 是否已有等价能力可扩展，而非新建一套并行实现
- [ ] `~/Public/tech-knowledge/` 是否有相关经验（作者是否查过）
- [ ] 是否存在两套语义重叠的数据模型（新旧并存但方案没说清迁移/收口）

### 0.5 Gate 0 结论

```markdown
### Gate 0：基线感知 —— 通过 / 打回

- 方案标注基线：`<commit>`（<日期>）| 未标注
- 当前 `origin/main`：`<commit>`（<日期>）
- 方案基线落后：<N> 个 commit
- 各仓库偏离：<repo>: 落后 N；<repo>: 落后 M

**否定结论复核表**

| 方案断言 | 验证命令 | 结论 |
|---|---|---|
| 「无 X 能力」 | `git grep -niE "..." origin/main` | 不成立 —— `path:line` 已实现 |

**已存在但方案未感知的资产**：<逐条列出，附路径>
```

任一条成立即 **打回**，不进后续数据清单：

- 方案未标注基线，或基线不是 `origin/<默认分支>`
- 方案基线落后 > 20 commit 且否定结论未复核
- 复核发现任一「不存在」断言不成立（已有实现 / 已有表 / 已有字段）
- 发现方案在重复建设 `origin/main` 上已有的数据模型

打回时给出已有实现的路径和覆盖范围，让作者判断是扩展还是确实需要新建，不代替作者做决定。

## 维度一：数据模型与迁移

方案里最贵的错误是数据错误。本维度独立于工程实施评审。

### 前置动作（Gate 0 通过后）

1. **读方案全文**，特别是数据模型变更和迁移章节。

2. **拉取真实 schema**。对着 `origin/main` 的 migration 仓和 model 定义，不看方案的描述：

   ```bash
   git grep -niE "create table|alter table" origin/main -- "*.sql"
   git show origin/main:path/to/schema.sql
   ```

3. **确认数据规模**。当前行数、日增量、峰值 QPS。拿不到真实数据时明确标注是估算，并要求作者补充。

### 1. 数据模型正确性

- [ ] 每张表有明确的**唯一职责**，不是「什么都往里塞」的宽表
- [ ] 主键选择合理（雪花 ID / UUID / 自增），跨环境和分库场景下不会冲突
- [ ] 字段语义与命名一致：`character_id` 存的就是 character id，不是 prefix、不是复合值
- [ ] 枚举字段有明确取值集合和默认值，新增取值时老代码行为已定义
- [ ] 时间字段统一时区语义（UTC vs 本地），类型统一（timestamptz vs bigint 毫秒）
- [ ] 金额、计数、配额类字段用整数或 decimal，不用 float
- [ ] JSON / JSONB 字段有明确 schema 约定，不是无结构垃圾桶；需要查询的字段不埋在 JSON 里
- [ ] 软删除 vs 硬删除策略明确，且与唯一索引不冲突

### 2. 约束与完整性

- [ ] NOT NULL、唯一约束、外键（或应用层等价校验）覆盖真实业务不变量
- [ ] 唯一索引的列组合与业务唯一性定义一致（含软删除列的处理）
- [ ] 默认值不会让新写入的行处于非法业务状态
- [ ] 并发写入下的唯一性保证方式明确（DB 约束 / 分布式锁 / 幂等键）

### 3. 一致性与事务

- [ ] 事务边界明确，跨表写入在同一事务内
- [ ] 跨服务写入的一致性策略明确（Saga / 补偿 / 最终一致 + 对账），不是「假设都会成功」
- [ ] 幂等键设计：重试、消息重投、客户端重复提交都不会产生重复数据
- [ ] 缓存与 DB 的一致性策略（失效时机、脏读窗口、缓存穿透）
- [ ] 消息队列消费的 at-least-once 语义下，消费逻辑幂等

### 4. 查询与性能

- [ ] 每个新查询模式都有对应索引；索引列顺序与查询谓词匹配
- [ ] 无全表扫描的高频查询；无缺 LIMIT 的无界查询
- [ ] 无 N+1：批量场景用 IN / JOIN / 批量接口
- [ ] 分页方式明确（offset vs cursor），大 offset 场景已考虑
- [ ] 排序字段有索引支撑，不依赖内存排序大结果集
- [ ] 索引数量与写入放大权衡过，没有为一次性查询加永久索引
- [ ] 大表的 count / aggregate 有替代方案（计数表、近似值、异步统计）

### 5. 迁移安全

- [ ] DDL 是否阻塞：加列带默认值、加索引、改类型在目标 PG 版本上的锁行为已确认
- [ ] 大表迁移有分批 / 在线方案，不是一条 UPDATE 全表
- [ ] 迁移可逆：down 脚本存在，或明确说明不可逆及理由
- [ ] 新旧代码并存窗口内 schema 兼容（先加列 → 双写 → 切读 → 删列，不一步到位）
- [ ] 数据回填脚本幂等、可中断续跑、有进度可观测
- [ ] migration 落到正确的仓库目录 / 环境 / schema，实例名和库名对应关系已核对

### 6. 数据生命周期

- [ ] 数据增长上限估算：一年后的行数和存储量
- [ ] 归档 / 清理策略，或明确说明永久保留及成本
- [ ] 敏感数据（PII、凭证、token）的存储方式、加密、访问范围、留存期
- [ ] 日志与埋点数据不混进业务表

### 7. 兼容性

- [ ] 老客户端读到新字段 / 缺字段时的行为已定义
- [ ] 接口字段语义变更是否破坏现有调用方，是否需要新版本而非原地改
- [ ] 已有数据在新语义下是否合法；不合法的部分有清洗方案

## 维度二：表述可读性（说人话）

判断标准不是「用词是否高级」，而是**一个懂业务但没参与本次设计的人，能不能一遍读懂**。

### 8. 首次出现的概念必须就近解释

- [ ] 每个自造概念 / 内部术语 / 字段名，首次出现时在同句或紧邻位置解释了它是什么
- [ ] 解释在**前**、术语在**后**（先说人话，术语挂括号里），不是先抛术语再指望读者往后翻
- [ ] 缩写首次出现时展开（`OC` → Original Character，用户捏的原创角色）
- [ ] 没有「详见下文」式的前置依赖 —— 读者读到那一句时就该懂

**反例 → 正例**（真实案例，均出自同一份方案的第一次稿）：

```
反例：把「图怎么用」从代码猜变成声明式管线开关（input_spec.image.role），
      并支持把该选择下放给用户（user_choice）。
      ↑ 「声明式管线开关」是什么？「下放给用户」下放的是什么？读者不知道。

正例：用户上传的图有两种用法 —— 拿它当参考重画一张（restyle）或直接把它
      当角色形象（as_is）。现在代码靠匹配 seed 里的 template.flow ==
      "pet_to_human" 字符串来猜走哪种，改成模板显式声明一个字段
      （input_spec.image.role）；模板也可以声明第三种取值 user_choice，
      表示「这个由用户在承接页自己选」。
```

```
反例：抽卡从只服务 pet 一条路径扩到全部模板，并区分两种作用域
      （会话级 / 逐候选级），把抽样结果落记录。
      ↑ 「抽卡」是什么？「作用域」指什么？为什么要分两种？

正例：抽卡（模板 seed 里写成候选池的字段，生成前随机抽一条，让同一模板
      每次捏出的角色不一样）现在只对宠物模板生效，扩到全部模板。同时区分
      两类抽法：身份类字段（性格、身世、关系）整个会话只抽一次，因为 5 张图
      得是同一个人；画面类字段（画风、色调）要为 5 张候选图各抽一套，这样
      5 张才是同一个人的不同风格照。
```

```
反例：管线只有两个分支轴。
正例：整条生成流程只在两个地方分叉，各是一个是非题：① 这次会话有没有
      用户图？—— 决定 persona 与出图各用哪份 prompt；② image.role 是不是
      as_is？—— 决定要不要跳过出图这一步。
```

### 9. 高优先级段落必须先说人话

以下位置是读者的主要入口，行话密度必须最低：

- [ ] **背景与目标 / 需求拆解** —— 每条目标先说「现在什么样、要变成什么样、为什么」，再挂术语和文件名
- [ ] **总体技术方向** —— 结论先落地成一句人话，再展开
- [ ] **Decision Log 的「决策」列** —— 决策内容本身要能独立读懂，不能只有「改用 X 模式」
- [ ] **风险清单** —— 每条风险说清「会发生什么后果」，不只说「有 X 风险」
- [ ] **验收标准** —— 用可观察的现象描述，不用内部实现词汇

### 10. 名词堆叠与抽象黑话

- [ ] 没有连续 3 个以上抽象名词拼成的短语（「声明式管线开关」「分支轴收敛」「不变量约束」）
- [ ] 用到以下词时，同句或紧邻位置有具体解释或例子：
      `声明式` `管线` `分支轴` `不变量` `正交` `收敛` `钳制` `兑现` `作用域` `拓扑` `语义`
- [ ] 比喻和抽象说法后面跟得上具体的东西（文件名、字段名、具体行为）
- [ ] 没有「优雅」「干净」「合理」这类无法验证的形容词充当理由

**这些词本身不禁用** —— 技术方案里它们往往是最准确的表达。要求是**就近有解释**。「不读 seed，与 V2 schema 正交」可以接受（后半句解释了前半句是什么意思）；「与 V2 正交」单独出现不行。

### 11. 读者视角与一致性

- [ ] 术语全文一致：同一个东西不在不同章节叫不同名字
- [ ] 「端」「方」用词准确：只有一个客户端就不写「三端」（应写「后端 / 客户端 / 运营配置三方」）
- [ ] 涉及多方协作时写明「谁做什么」，不留「需要客户端配合」这类无主语句
- [ ] 代码位置引用到 `file:line`，让读者能自己去核
- [ ] 数字有出处：「10 处使用点」要么列出来，要么给出搜索命令

### 12. 结构可读性

- [ ] 长表格前有一句话说明「这张表在回答什么问题」
- [ ] 大段代码 / JSON 前后有说明，不是甩一段 schema 让读者自己解读
- [ ] 推翻旧决策时标注了「推翻了什么、为什么」，不是直接覆盖让读者对不上历史
- [ ] 待确认项写明「谁来确认、不确认会阻塞什么」

## 输出格式

Gate 0 结论必须放在最前面。Gate 0 打回时只输出 Gate 0 部分，不要补后续维度的结论 —— 基线错了，后面的评审是白做的。

```markdown
## 技术方案评审结论：通过 / 有条件通过 / 打回

- Gate 0 基线感知：通过 / 打回（详见上方复核表）
- 方案基线：`<commit>`（<日期>）；当前 `origin/main`：`<commit>`（<日期>）；落后 <N> commit
- 评审范围：<方案文档路径 / 章节>
- 已跑维度：数据模型与迁移 / 表述可读性

### CRITICAL（必须改，会导致数据错误或不可逆损失）
1. **<问题>** — <依据：表/字段/查询/迁移语句>。<后果>。建议：<具体做法>。

### HIGH（上线前应改，会导致性能问题、兼容故障，或方案关键部分无法被读懂）
### MEDIUM（建议改，影响长期维护或阅读效率）

### 表述可读性问题
逐条给出「原文 → 建议改法」，原文引用带章节号或行号。不要只说「这里不好懂」。

### 已确认无问题的项
简要列出重点检查过且没问题的维度，让作者知道哪些不用返工。

### 需要作者补充的信息
逐条列出评审无法定论、必须作者提供数据或说明的点。
```

## 边界

- **评审范围**：Gate 0 基线感知 + 数据模型与迁移 + 表述可读性。代码结构、分层、测试覆盖交给 `code-structure-review`；范围边界、分支策略、发布依赖、实施计划交给 `plan-eng-review`。
- **不提代码风格意见**（变量命名、格式、注释密度）。**文档**的表述可读性属本 skill 范围，**代码**的可读性不属。
- 不建议重构、不建议改架构。只报数据正确性、一致性、性能、迁移安全、兼容性，以及方案是否能被读懂。
- 表述可读性问题必须给出**具体改法**，不能只标记「难懂」。给不出改法说明评审者自己也没读懂 —— 那就转为「需要作者补充说明」，不要硬编一个改法。
- 表述可读性不是文字洁癖：**只报影响理解的问题**，不报个人文风偏好。判据是「换个人读会不会误解或读不懂」，不是「我会不会这么写」。
- 独立验证，不因为方案作者是 AI 或人就降低标准。方案里的断言要自己对着代码和 schema 核实。
- 拿不到真实数据规模时不硬下结论，标注为「需补充」。
- **Gate 0 不可跳过、不可为了推进而放水。** 方案质量再高，基线错了也是重复劳动。落后 > 20 commit 且未复核否定结论时，一律打回。
- Gate 0 打回时只给已有实现的路径和覆盖范围，让作者决定「扩展已有」还是「确实要新建」。不代替作者改方案。
