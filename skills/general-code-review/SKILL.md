# 通用 Code Review

对被多处消费的依赖做覆盖面体检，对跨边界标识符做精度完整性检查。只读；除非用户明确要求，不改被审代码。

根据 diff 回答适用的问题：

- **依赖覆盖**：这次改造是否覆盖了该依赖的全部消费点；没覆盖的是否是有意保留。
- **标识符完整性**：标识符从生产到消费是否保持逐位一致，是否可能因浮点数或隐式类型转换映射到另一主体。

不查结构好坏（那是结构评审的活），不做与上述两类风险无关的算法审查，不提格式偏好。

## 什么时候用

diff 命中以下任一类，就该跑这个评审：

- 凭证类：api key、secret、token、GSM/Vault secret 映射、鉴权 header
- 端点类：base URL、host、网关地址、外部服务 endpoint
- 客户端类：新增 client 变体、`ForXxx()` 派生 client、连接池、带不同配置的实例
- 分流类：按开关/灰度/版本走新旧两套下游
- 共享配置：被多个调用路径读取的 model 名、超时、限流、重试策略
- 标识符：用户 ID、订单 ID、会话 ID、任务 ID、Snowflake、`int64/uint64` ID
- 弱类型边界：JSON、JWT `MapClaims`、`map[string]any`、RPC metadata、消息事件、URL、Cookie、LocalStorage
- JavaScript 边界：后端长整数进入 JS/TS，或前端出现 `Number(id)`、`parseInt(id)` 后再传回

判据不是「改了几行」，而是**这个字段/实例有没有第二个消费者**。有就跑。

标识符精度模式不要求存在第二个消费者；只要标识符可能跨弱类型或 JavaScript 边界就跑。两种模式同时适用时都执行。

## 核心动作：先建 consume map，再看 diff

顺序不能反。先看 diff 会被 diff 框住视野，只看见改了的地方，看不见没改的地方。

### 第一步：枚举消费点（不看 diff）

从**定义处**出发，而不是从改动处出发。

```bash
git fetch --prune
# 1. 找到该字段的注入点（config → client 构造）
git grep -nE '<字段名>|<Option 名>' origin/main
# 2. 找到该字段在实现里的全部读取点
git grep -nE '\.<字段名>\b' origin/main
# 3. 顺着读取点反查调用链，直到每条都落到一个业务入口
```

关键：**读取点不等于消费点**。一个 `c.apiKey` 的读取点可能被 5 个业务入口共享。要一路往上追到「用户/定时任务/worker 触发的那个入口」为止。

常被漏掉的消费点类型（逐类确认，不要凭印象跳过）：

| 类型 | 为什么容易漏 |
|---|---|
| 前置准备步骤 | 主流程改了，但它先要上传/预处理/建资源，那步单独发请求 |
| 轮询 / 查状态 | 提交改了，查询还在老实例上 |
| 异步 worker / 队列消费者 | 与同步入口不同文件，grep 主流程时不出现 |
| 定时任务 / 补偿重试 | 平时不跑，测试期不触发 |
| 创作态 / 预览 / 草稿路径 | 与正式路径逻辑相似但独立实现，复用的是子函数不是主流程 |
| 后台 / admin / 运营工具 | 不在 C 端回归范围内 |
| 回滚或兼容分支 | 老路径故意留着，容易被当成「已经不用了」 |

### 第二步：产出覆盖矩阵

每个消费点一行，必须落三列：

| 消费点（入口 → 调用链） | 用的是哪套（host / key / 实例） | 本次是否覆盖 |
|---|---|---|
| `EntryA` → `worker` → `client.ForNew()` | 新 | 是 |
| `EntryB` → `sharedHelper` → 默认 client | 旧 | **否，未纳入** |

三列都要有依据（文件:行号）。**「否」不是错误,但必须是显式结论**,不能是空白。

### 第三步：对每个「否」问三句

1. 是有意保留，还是漏了？
2. 如果有意保留，旧那套现在还有效吗？（旧凭证是否还没过期、旧 host 是否还在服务）
3. 用户/测试能不能触发它？能触发 + 旧那套已失效 = 本次改造引入的可复现故障

第 2、3 条同时成立时，按 CRITICAL 报。这是最典型的漏改事故形态：主路径验证通过、放量 100% 也正常，但另一条共享同一份凭证的路径已经在报鉴权失败。

## 标识符精度模式：追踪完整往返链路

用户 ID、订单 ID、会话 ID、任务 ID、Snowflake ID 等只用于唯一定位和相等比较的值是**不透明字符串**，不是可计算数值。数据库内部可使用 `BIGINT`，后端强类型内部可使用 `int64`；一旦进入 JSON、JavaScript、JWT 通用 claims、消息、缓存或其他弱类型边界，必须以字符串传输和解析。

先从标识符定义处枚举完整链路：

```text
生成/数据库 → DTO/claim/event → 序列化 → 传输/缓存 → 反序列化 → 鉴权/查询/比较
```

每个标识符输出一行：

| 标识符 | 完整链路 | 跨边界表示 | 是否经过浮点数 | 本次是否覆盖 | 结论 |
|---|---|---|---|---|---|

重点检查：

- Go 等库把 JSON number 或 JWT claim 默认解码成 `float64`，再执行 `int64(v)`；
- JS/TS 使用 `Number(id)`、一元 `+id`、数值型 schema，或把长整数作为 JSON number 读写；
- 先发生精度丢失，再通过 `String(v)`、格式化或整数转换试图恢复；
- 登录响应已改成字符串，但刷新 Token、后续鉴权、middleware context、异步任务、缓存键或埋点仍走数值；
- 新旧协议并存时，只检查了签发端，没有枚举全部 Token/事件消费者；
- 通过 ID 大小、位段或前缀推断业务属性，而不是使用显式字段。

`float64` 和 JavaScript `Number` 只能精确表示到 `2^53-1`。只要原始标识符可能超过该范围，经过浮点数就是数据完整性问题；转换后的值仍“看起来像整数”不能证明安全。`UseNumber`、`WithJSONNumber` 等可用于兼容既有数值协议，但新协议应直接使用字符串。

验证不能只用小整数。至少覆盖 `2^53-1`、`2^53`、`2^53+1`、真实生产量级 ID，以及一组会在 `float64` 中碰撞的相邻 ID；逐个验证序列化前后十进制文本完全一致。身份或资源 ID 能稳定映射到另一真实主体时按 CRITICAL 报。

## 常见错误模式

### 模式一：分流只做在主路径

新旧分流写在主流程的分支里，其他入口调的是**分流之前的那个共享函数**，于是永远走默认（旧）那套。

```go
// 主路径：看开关，切到新实例
if snapshot.NewPathEnabled {
    resp, err = client.ForNew().Submit(ctx, req)   // 新 host + 新 key
} else {
    resp, err = client.Submit(ctx, req)
}

// 另一个入口：直接调共享 helper，helper 内部只有默认实例
// → 它永远走旧 host + 旧 key，开关拉到 100% 也不影响它
func (s *Service) callShared(ctx context.Context, p *Params) (string, error) {
    return s.client.Submit(ctx, p)                 // 没有 ForNew() 分支
}
```

审的时候不要只确认「分流分支写对了」，要确认**分流点在调用链上的位置足够靠下**，让所有入口都经过它；或者确认每个入口都各自做了分流。

### 模式二：静默回退把配置缺失藏起来

```go
key := strings.TrimSpace(c.newKey)
if key == "" {
    key = c.oldKey     // 本意是本地调试方便
}
```

这类回退会把「新环境没配 secret」变成「静默用旧 key 打新 host」，报错点跑到远端鉴权失败,离根因很远。审的时候确认：回退是否只该在本地生效、是否有日志把实际用的是哪套打出来、生产是否有校验拦住空值。

### 模式三：提交与查询用了不同实例

提交走新 host 拿到 id，轮询走默认实例去老 host 查，永远查不到或报不存在。凡是「提交 / 查询 / 取消 / 回调」成组出现的操作，要确认它们绑的是同一个实例。

### 模式四：以主路径验证结论覆盖全局

「灰度 100% 已验证通过」只证明被验证的那条链路。报告里不能把它写成「该依赖改造已完成」。验证结论的作用域必须写清是哪个入口。

### 模式五：标识符先转浮点数再转回来

```go
claims := token.Claims.(jwt.MapClaims) // JSON number 已成为 float64
userID := int64(claims["user_id"].(float64))
```

当 ID 大于 `2^53-1` 时，低位可能在第一行解析时已经丢失，第二行无法恢复。修复必须前移到 wire contract 或反序列化入口，并继续检查所有消费同一 claim 的鉴权路径。

## 报告格式

```
## 消费点覆盖矩阵
（依赖覆盖模式适用时输出；全部消费点，含未覆盖的）

## 标识符完整性矩阵
（标识符精度模式适用时输出；覆盖生产、传输、解析和最终消费）

## CRITICAL / HIGH / MEDIUM 问题
- [级别] <消费点> 仍走旧 <host/key>，且旧凭证已失效 → 可触发路径：<怎么触发>
  证据：file.go:123（读取点）、file.go:456（分流点缺失）
  影响：<具体表现，如某步骤鉴权失败>

## 覆盖面结论
- 已覆盖：N 个入口
- 有意保留旧路径：M 个（逐个说明为何安全）
- 疑似漏改：K 个
```

没发现问题时，依赖覆盖模式直接说「全部 N 个消费点已覆盖」；标识符精度模式直接说「全部 N 条标识符链路均保持逐位一致」。附上适用矩阵，证明枚举过而不是没看见。

## 边界

- 只报本次改造引入或加剧的覆盖缺口，不清算历史遗留的多路径实现
- 不因为「存在第二条路径」就要求统一，路径分叉可能是有意设计；只要求**结论显式**
- 枚举以默认分支（一般 `origin/main`）为基线,不以当前工作区为基线;结论写明 revision
- 得出「只有一个消费点」这类否定结论前,在默认分支上复核一遍再回复
