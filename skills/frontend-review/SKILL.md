# FE 前端评审

保持前端变更可读、可评审，并按职责划分。优先使用清晰的领域名称，避免在大组件中堆积内联实现。默认只读；用户明确要求实现或重构时，使用文末已有的实现清单。

## 评审前定位

评审或编辑前先确认：

- 框架和项目现有约定。
- 本次涉及的文件和行数。
- 改动属于页面级功能、复用 UI、数据转换、样式调整还是有状态行为。
- 检查实际调用关系，确定新增或抽取的组件、hook 所属的最小范围，并统计该范围内已有的同类实现。
- 项目已有测试规则；项目明确禁止时不新增测试。

## 现有结构约定

- 前端文件保持在 400 行以内；已有文件超过 400 行时，不继续扩大，能按职责抽出本次修改部分时进行收敛。项目已有明确规则时以项目为准。
- 在组件难以阅读前按职责拆分。
- 避免千行页面，以及请求、格式化、常量、事件逻辑和密集 JSX 混在一个文件。
- Tailwind 类名遮蔽意图时，检查可读性。
- 提取部分按领域行为命名。
- 优先采用小而清晰的模块，避免无价值的泛化抽象。

## 目录归属与渐进归组

先判断归属，再按数量归组。目录表达代码所有权，不机械复制 JSX 的嵌套层级。

- **私有实现就近放置**：组件拥有独立拆出的私有实现时，使用同名目录，`index.tsx` 作为入口。私有子组件、hooks 和样式放在该目录内，不与所属组件平铺；纯展示组件也遵循归属关系。
- **超过 3 个主动归组**：同一归属范围内，自定义 hook 或子组件超过 3 个（第 4 个起），分别收敛到该范围的 `hooks/`、`components/`。统计自有实现，不计 React 内置 hooks、外部导入组件或 JSX 使用次数。数量较少时允许在所属目录内平铺；已有分类目录则继续复用，不要求凑够 4 个。
- **真实复用再上提**：多个独立调用方确实需要、且职责与语义一致时，才移到最近的共同所属范围。不要因“以后可能复用”提前上提，也不要因为有两个调用方就直接移到全局共享目录。
- **随改动维护**：新增第 4 个同类实现时，在本次涉及范围内主动完成归组并更新引用，不等待用户 review 时提醒，不顺带重排无关目录。
- **保持边界**：外部调用方使用所属组件的公开入口，不跨目录引用其私有实现；出现真实共享需求时按上述规则上提。

例如，一个功能既有共享 hooks，也有包含私有子组件的视图，可以逐步形成：

```text
feature-name/
  index.tsx
  hooks/
    use-feature-state.ts
    ...
  detail-view/
    index.tsx
    components/
      detail-item.tsx
      ...
  const.ts
  utils.ts
  types.ts
```

只创建确有职责的文件或目录；仅服务 `detail-view` 的 hooks 放在该视图内部，不放到功能共享层。

- `index.tsx`：组合、数据连接与主组件导出，不为所有分类目录机械新增 barrel 文件。
- `ui.tsx`：少量且内聚的展示子结构；子组件超过阈值时拆到 `components/`，不靠堆进一个文件规避归组。
- `const.ts`：静态选项、超时、映射、标签、路由。
- `utils.ts`：内聚的纯计算、解析、格式化与选择逻辑。
- `types.ts`：会使其他文件臃肿的局部共享类型。
- 测试文件：仅在仓库规则允许时添加。

不要为了符合示例而创建空目录或无职责文件。

## Tailwind 可读性

简单元素可以直接使用内联 Tailwind。以下情况考虑提取：

- JSX 节点类名很长，且没有表达语义的名称。
- 同级元素重复使用同一组类名。
- 样式表达了状态、布局或产品语义。
- 周围 JSX 需要注释才能解释该元素的职责。

可采用下列有明确语义的结构：

```tsx
export function LiveRoomBackgroundCarousel() {
  const currentScene = useCurrentBackgroundScene();

  return (
    <img
      src={currentScene.src}
      alt=""
      className="absolute inset-0 h-full w-full object-cover opacity-95"
      draggable={false}
    />
  );
}
```

避免将重要视觉行为作为匿名内联元素埋在大组件中。

## 提取规则

提取后的名称应帮助读者理解：

- 用 `sceneIndexForHour` 表达时间窗口计算，避免将计算埋在 JSX 中。
- 存在轮换、选择或业务语义时，用 `LiveRoomBackgroundCarousel` 表达职责。
- 用 `BACKGROUND_GROUP_ROTATE_MS` 表达定时常量的含义。

提取会降低清晰度时不要提取：

- 避免 `ImageBox` 等仅包装原始 HTML 的一次性组件，除非承载真实行为。
- 避免把杂项堆进 `helpers.ts`；`utils.ts` 只放内聚的局部纯函数。
- 不把每个 Tailwind 类都抽成常量；提取有语义的部分。

## 评审清单

评审前端变更时依次检查：

1. 归属与目录：是否有私有实现与所属组件平铺、超过 3 个仍未归组、跨目录引用私有实现，或尚无真实复用就提前上提？按“目录归属与渐进归组”检查。
2. 文件体量：本次涉及的文件是否超过或接近 400 行？
3. 职责拆分：常量、纯逻辑、UI、数据连接和类型是否混杂？
4. JSX 可读性：主组件能否在一屏内理解？
5. Tailwind 密度：类名是否遮蔽重要 UI 的意图？
6. 命名：抽取的组件和辅助函数是否描述业务行为？
7. 验证：是否遵循仓库规则完成适当的类型、lint、构建或浏览器检查？

意见应指向具体边界，例如：

```text
将时间窗口计算移到 utils.ts 的 sceneIndexForHour()，组件保留选择与渲染。
```

## 用户明确要求修改时的实现清单

实现前端变更时：

1. 先检查实际调用关系与本地约定，确定组件、hook 的归属和共享范围。
2. 按“目录归属与渐进归组”放置私有实现；达到阈值时主动整理目录并更新引用。
3. 保持 `index.tsx` 为组合入口。
4. JSX 变得密集之前，先分离纯逻辑和常量。
5. 本次涉及的文件超过 400 行之前主动拆分。
6. 交付前复查目录归属、数量阈值和引用边界，并执行仓库要求的验证。

## 通用结构检查与报告

以下规则来自原代码结构评审：只报告本次新增或明显加剧的问题；纯移动不算新增问题，风格偏好不形成 finding。

- 同一业务决策应有一个权威落点，读写路径共享规则但分别保留副作用；代码形状相似不等于业务语义相同。
- 共享状态和生命周期具有明确所有者；无状态计算保持纯函数，避免隐藏的入参修改和调用顺序要求。
- 抽象应承载不变量、状态或副作用边界、真实复用或依赖隔离；单调用点本身不构成问题，不为缩短主文件制造透传包装。
- 用语义名称展示主要阶段；注释在最窄的规则或状态所有者处解释原因和不变量，不重复叙述操作。
- 明确基线、覆盖文件及已提交/暂存/未暂存/未跟踪范围。行为等价未经验证时标为未知。

报告结论、具体文件行号、证据与影响、建议的职责边界，以及未确认项。同一根因合并报告；没有结构问题时明确说明，不为了填模板制造发现。

## 涉及共享依赖或跨端契约时

FE 改动涉及凭证、端点、client、共享配置或 `Number(id)` 等标识符转换时，继续按原通用专项检查全部消费点与 ID 完整性。按需读取同仓库 [BE 消费点与 ID 专项](../backend-review/references/dependency-and-identifiers.md)，只执行适用模式，不重复运行整个 BE 评审。

涉及配置及发布资源时，读取 [结构参考](../backend-review/references/structure.md)中的“配置改动 = 发布依赖门禁”，保留原配置清单、权威文档核对与未知项报告。

上述跨端检查依赖同时安装 `backend-review`；材料不可用时明确标记该维度未核验，不声称完整通过。
