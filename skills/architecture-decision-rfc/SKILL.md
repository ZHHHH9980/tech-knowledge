# 架构评估与决策

用于把“想法讨论”收敛为“可执行方案”。

## 使用方式

1. 收集输入：背景、现状、目标、约束、非目标、时间窗口、PRD、Figma 和现有实现。
2. 判断是否涉及用户可见页面或交互：
   - 适用时实际读取相关 Figma 页面、节点、原型连线和注释，提取状态、动作、异常分支和数据需求。
   - 无法找到或访问 Figma 时，将其列为阻塞方案完整性的待确认项，不凭经验补全。
   - 纯基础设施或无 UI 变更时，明确记录“Figma 不适用”及理由。
3. 对照 PRD、Figma、Tech Design 和现有实现；存在冲突时列出差异、影响和待确认决策，不自行选择一种解释。
4. 按 [template.md](template.md) 输出完整方案。
5. 用 [checklist.md](checklist.md) 做评审前自检。

## 固定输出结构

1. 问题陈述
1.1 架构范式差异
1.2 依赖拓扑
1.3 组织因素
1.4 Figma 交互证据与契约缺口

2. 方案评估
2.1 备选方案
2.2 评估
2.3 决策
2.4 被否定方案的参考价值

3. 目标架构
3.1 分层模型
3.2 调用链路与网关策略
3.3 URL/协议/契约设计
3.4 交互状态与后端契约
3.5 依赖方向与所有权

4. 落地推演
4.1 仓库与模块改造清单
4.2 迁移阶段计划（Phase 1/2/3）
4.3 兼容与回滚策略
4.4 风险清单与缓解动作
4.5 验收标准（Done Definition）

## 评估规则

- 先定义问题，再比较方案，再做决策，不要倒序。
- 每个结论都标注依据：事实、数据、约束、假设。
- 用户交互类结论必须标注对应的 Figma 页面或节点，并覆盖主路径、loading、空态、失败、重试、取消和重复操作。
- 将每个关键交互映射到接口、字段、状态所有者、后端副作用、幂等/并发规则和用户可见结果。
- 方案评估至少覆盖：复杂度、成本、风险、扩展性、团队匹配度。
- 决策必须写清 trade-off：得到什么、失去什么、为什么可接受。
- 落地计划必须可执行：阶段目标、灰度方式、回滚条件、验收口径。

## 写作约束

- 避免空泛词：如“更好”“更优雅”，必须量化或举例。
- 避免只有结论没有路径；必须给可执行迁移步骤。
- 避免只讲选中方案；被否定方案也要写参考价值。
- 不把 Figma 当作唯一真相源；PRD、Figma、Tech Design、接口定义和现有实现冲突时，必须显式记录并推动决策。
