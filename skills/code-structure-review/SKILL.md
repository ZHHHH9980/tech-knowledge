# 代码结构评审

实现完成后的结构体检，只读。除非用户明确要求，不改被审代码。

关注结构和可维护性：规则有没有分叉、状态归谁管、抽象值不值、体量是否失控、配置有没有漏登记。

不猎 bug（那是 code review / 安全评审的活），不追覆盖率数字，不提格式化偏好。

## 前置动作

```bash
git status --short --branch
git fetch --prune
git diff --stat <base>...HEAD     # 已提交改动全貌
git diff <base>...HEAD            # 已提交改动
git diff --cached                 # 暂存改动
git diff                          # 未暂存改动
git ls-files --others --exclude-standard
```

`<base>` 的优先级：用户指定基线 → MR/PR target → 当前分支 upstream 或远端默认分支。不要默认所有仓库都是 `origin/main`。用户给了明确 diff、commit、MR/PR 或文件范围时，以用户范围为准。

未跟踪文件若属于本次实现，要读取内容并纳入评审，不能因为 `git diff` 看不到就漏掉。无法安全确定基线时，说明当前可见范围和未知项，不虚构完整性。

四件事：

1. **读上下文，不只读 diff 片段**。判断职责归属要看完整文件和相邻同层实现。
2. **对齐项目既有模式**。同层其他文件怎么写，本次就怎么写，不引入项目里没有的新范式。
3. **区分三类问题**：本次新增的、本次明显加剧的、与本次无关的历史债务。只报前两类。
4. **覆盖全部改动形态**。分别核对已提交、暂存、未暂存和未跟踪文件；报告里写明实际覆盖了哪些范围。

纯移动、重命名、机械拆文件按语义比，别因为在 diff 里显示为新增就把旧债算成本次引入。

## 一、业务规则只能有一处决策点

这是最重要的一条。阈值、状态迁移、时间窗口、资格判定、计费、权限、幂等规则，追踪所有消费者：写入/落库/定时结算、查询/展示/预演、同步/异步/重试/恢复、缓存/事件/通知/外部调用。

**变更放大测试**：假设改一个阈值，要动几处分支？动多处就是没收敛。

```go
// 分叉了：同一条「过期」规则写了两份，改 7 天要改两处
func (s *Service) Settle(ctx context.Context, order *Order) error {
    if time.Since(order.CreatedAt) > 7*24*time.Hour { ... }
}
func (s *Service) ListOrders(ctx context.Context) ([]OrderVO, error) {
    for _, o := range orders {
        vo.Expired = time.Since(o.CreatedAt) > 7*24*time.Hour  // 第二份
    }
}

// 收敛后：规则一份，副作用各自保留
func (o *Order) IsExpired(now time.Time) bool {
    return now.Sub(o.CreatedAt) > orderTTL
}
```

规则函数保持无副作用；查询、落库、通知各自留在自己的调用点。读路径和写路径可以共享状态判断，但不要为了复用把只读投影和状态写入混成一个带隐藏副作用的函数。

代码长得像不等于该复用。只有业务语义、不变量、未来变更原因都相同才共享。

## 二、状态归谁管要清楚

一组操作共享同一份可变状态、配置、不变量和固定执行顺序时，让一个内聚的对象 / receiver / 模块承载它，稳定依赖放在它身上，每次操作独有的事实留作显式参数。

看到这些先查：

- 多个自由函数反复传同一份 `state` / `settings` / 事务 / context
- 同一状态机的推进步骤散在几个没有独立语义的 helper 里
- 主流程很短，但读者得跨好几个包装类型追同一份状态
- 任意函数都能改状态，没有单一入口维护生命周期和顺序
- 对象先以不完整状态构造，再由 `prepare` / `init` / `hydrate` 原地补齐（走第九章两个测试）

无状态纯函数保持独立，别机械改成 method。也别把互不相关的生命周期塞进一个「大管家」对象。

## 三、抽象要有净价值

本次新增或修改的私有 type / struct / helper / wrapper / hook / component，每个至少要提供一项：承载独立不变量或领域概念、划定状态或副作用的所有权边界、被多个真实调用点复用、隔离外部依赖或兼容分支、减少规则的修改点。

收敛信号（不是继续拆的理由）：

- 只在一个地方构造、只为向下透传参数的包装 struct
- 只转调下一个函数、没有新增策略或边界的 helper
- 围着同一份可变状态造出多个一次性参数载体
- 提取后主流程短了，但真实业务顺序散进更多文件和跳转

单调用点本身不是问题。只调一次但承载了不变量、策略边界、可测试契约或复杂隔离，就是有价值的。报告时必须说清缺的是哪项价值，不能只数调用次数。

## 四、主流程是编排概要

核心入口直接展示业务阶段，不嵌详细条件、持久化细节、重试、清理、格式转换、兼容回退：

```go
func HandleRequest(ctx context.Context, request Request) error {
    input, err := validateRequest(ctx, request)
    if err != nil {
        return err
    }
    result, err := executeTransition(ctx, input)
    if err != nil {
        return err
    }
    return publishResult(ctx, result)
}
```

输入归一化、空状态、兼容分支、重试回退、部分失败恢复、幂等去重、资源释放、外部错误翻译，都留在聚焦的边界抽象里。

反面是「假短主流程」：每一步只是跳进另一个一次性 wrapper，读者仍然看不到状态所有者和规则顺序。这按抽象碎片化报。

## 五、分层与依赖方向

- 业务规则在 biz / domain 层，不散到 handler / logic / data
- 数据访问在 data / repository 层，biz 不直接拼 SQL
- service / handler 只做协议转换和编排，不含业务判断
- 协议形状转换集中在 adapter / mapper
- 没有跨层直接调用（handler 打 DB、data 层写业务分支）
- 依赖指向稳定的一侧，无包级 / 模块级循环依赖
- 跨服务调用集中在明确的 client 层
- 新增代码放在语义正确的包，不因为「改起来方便」就地塞
- 全局状态和单例的引入要有理由，不是为省参数传递

## 六、体量是信号，不是结论

先按项目已有规则。项目没规定时，手写源码接近或超过 400 行、函数接近或超过 50 行，当作深入检查信号。

只有确认文件或函数混了独立职责才报，并给出按领域划分的具体边界。生成代码、锁文件、vendored 依赖、机器生成的协议绑定、结构上必须单文件的数据 fixture，不机械标记。

大型手写 API schema、协议、配置、测试文件仍要看，但只在存在清晰领域边界时才建议拆。

配套检查：嵌套不超过 4 层，深嵌套用早返回展平；页面级复杂功能按 feature folder 组织。

## 七、命名

- 字段名、变量名表达实际存储内容，不是用途的某个侧面
- 函数名表达做了什么，不用 `handle` / `process` / `do` 这类泛化动词
- 布尔用 `is_` / `has_` / `should_` / `can_` 前缀
- 集合用复数名词；映射用 `xxx_by_yyy` 或 `xxx_map`
- 无无意义缩写（`msg` / `cfg` / `cb`），项目既有约定俗成的除外
- 新增 API 字段、DB 列、proto field 命名准确无歧义（发布后改成本极高）

## 八、参数结构按语义选

先执行项目已有的参数硬规则。项目没有规定时，三个以上同类依赖、或六个以上位置参数，当作检查信号，不机械要求参数 struct。

- 公开 use case 输入、稳定数据契约 → 具名 params struct
- 多步操作共享的状态和配置 → 内聚的 owner 或 receiver
- 单次操作独有的少量事实 → 显式参数
- 可选项多、默认值多的公共 API → 按项目惯例考虑 options

别只为满足数量规则造一个单调用点包装。建议时说清新结构表达的领域含义、所有权或不变量。

## 九、副作用要从签名可见

能算成 `输入 → 返回值` 的业务计算，不要靠改传入的 `*struct` / `map` / `slice`
传结果。调用方读不到函数体时，签名就是它唯一的契约。

两个测试，比列举坏味道管用：

**签名可见性测试**：只看签名，能不能答出「读了什么、写了入参的哪些字段、返回后
哪些字段才算有效」？答不出，数据流就是隐藏的。

**跳过测试**：把中间那步删掉。仍能编译、且下游会读到零值或未初始化字段 ——
说明「必须先准备」这个契约只活在作者记忆里，类型没兜住。

```go
// 两个测试都不过：签名只说「拿走 ts」，没说写了什么；
// 删掉 prepareTurn 照样编译，runFCLoop 静默读到零值。
ts := &turnState{ctx: ctx, session: session, input: input}
e.prepareTurn(ts)          // 无返回值，实际写入 systemPrompt/history/toolDefs
return e.runFCLoop(ts)     // 能跑只因为上一行执行过

// 阶段产物走返回值，顺序由类型强制
prepared, err := e.prepareTurn(ctx, input, session)
if err != nil {
    return TurnResult{}, err
}
return e.runFCLoop(ctx, prepared, writer)
```

即使两行紧邻也算问题：紧邻靠的是当下的代码顺序，不是契约。

不机械禁止指针和就地修改。归属明确的 accumulator、buffer、writer、事务、状态机
可以原地更新，前提是四条同时成立：对象由当前抽象拥有、签名或方法名讲清了这次
写入、没有别名修改、没有隐藏的调用顺序要求。

**错误**：

- 副作用可预期，不在 getter 里改状态；无隐式全局状态修改
- 共享数据的并发访问有保护；无裸 goroutine（走项目并发封装）
- 错误走项目既有纲领（错误码 / 包装 / 前端文案映射），在正确的层被处理或包装，不层层裸传也不就地吞掉
- 无静默吞错；错误文案语言符合项目约定

## 十、注释在最窄的所有者处

注释解释无法从操作本身推导的东西：生命周期、业务原因、不变量、正确性顺序。重点在状态机与时间窗口、计费与权益与配额、幂等与锁与 fencing 与 CAS、持久化/缓存/事件/外部调用之间的顺序、重试与 fail-open/fail-closed、协议版本与兼容分支、表面是读但会刷新或上报的隐藏写入。

```go
// 有效：先持久化终态再发布事件，确保重试保持幂等。
if err := finalizeSession(ctx, session); err != nil {
    return err
}

// 无效：结束会话。
```

说明放在规则函数、状态所有者或决策簇入口。短编排已经用领域方法名讲清步骤、顺序和不变量已在所有者处说明时，不要求调用点重复加逐步注释。只有调用点引入了额外的业务原因、跨抽象顺序或副作用约束，才要求就地注释。

函数因状态机推演、批量结算或原子写回等原因需要保留多个顺序阶段时，检查阶段边界、各阶段产物和写入责任是否能从结构或命名读出。只有业务目的、写入字段或先后不变量无法推导时才报问题；优先建议收敛阶段产物、提取有语义的步骤或补最窄位置的注释，不把“每段都必须有注释”当作机械规则。

其余：注释与文档用中文、标识符英文；无过期注释；TODO 已登记；无调试残留（print / console.log / 临时开关）。

## 十一、行为不变的重构要有测试守着

声称「行为不变」的重构，确认原有的状态边界、时间边界、错误路径、幂等、只读不写回等契约仍被覆盖。测试应迁到新的内聚 API，不要继续绕过所有者去调已废弃的内部碎片。

没跑测试就标记为未知，不要仅凭代码移动宣称等价。不为了结构指标要求删掉有价值的边界测试。

## 十二、配置改动 = 发布依赖门禁（固定项）

这条固定输出，即使没有结构 finding 也要报。

**扫描范围**（不只看名字像配置的文件）：

- 运行配置文件：`.env*`、YAML、TOML、JSON、properties、`etc/`、`config/`、Helm、K8s、部署脚本、基础设施清单
- 代码里的配置入口：环境变量读取、配置 struct 字段、启动参数、默认值、必填校验、Secret / ConfigMap 引用、secret manager key
- 运行行为参数：外部服务地址与凭证、feature flag、超时、限流、并发、重试、队列 / topic / 订阅、定时任务、IAM 权限、人工后台开关
- 配置项的新增、删除、重命名、默认值变化、必填性变化、语义变化 —— 即使配置文件本身没进 diff

**建配置清单**：配置项或资源、变更前后语义、消费服务、默认值与必填性、受影响环境。纯代码搬移且配置契约、取值、运行行为都没变时可判定为无发布依赖变化，但要给依据，不能只看文件名下结论。

**核对权威文档**：按项目规则定位（feature 的 `deploy-checklist.md`、发布清单、rollout runbook、团队共享发布依赖子文档）。项目已指定权威文档时，不能用代码默认值、MR 描述或本地备注替代。

发布依赖至少记录：配置项名称 + 影响服务 + Dev/UAT/Prod 的具体值或状态；启用条件、前置依赖、生效顺序、回滚方式；Secret / API key / token 的存放位置和引用名（不记明文值）。

**四种结论**：

| 情况 | 输出 |
| --- | --- |
| 有配置改动，权威文档缺失 / 漏项 / 还是旧值 | `P1`，明确写「先同步文档再发布」 |
| 文档在 diff 外、外部系统或当前访问不到 | 标「未确认」，列出待登记项并提醒用户；不默认已同步，也不虚构缺失 |
| 配置改动与权威文档逐项匹配 | 说明核对过的文档位置和配置项 |
| 没有影响部署或运行环境的配置改动 | 明确说明扫描结果，不省略该项 |

## 输出格式

```markdown
## 代码结构评审：通过 / 有条件通过 / 需返工

- 基线：`<base>` `<commit>`（<日期>），选择依据：<用户指定 / MR target / upstream / 远端默认分支>
- 覆盖范围：<已提交 / 暂存 / 未暂存 / 未跟踪 / 用户指定范围>
- 改动规模：<N 文件 / +A -B 行>，已排除生成文件：<列表或无>
- 是否修改被审代码：否

### Findings

1. `[P1][9/10]` 订单过期规则在结算与列表两处分叉
   `internal/logic/settle.go:88`、`internal/logic/list.go:142`

   两处各写一份 `time.Since(CreatedAt) > 7*24h`。改 TTL 要同步两处，漏一处会出现「列表显示未过期但结算已过期」。

   收敛到 `Order.IsExpired(now)`，两条路径各自保留查询和落库副作用。

### 发布依赖检查
- 配置改动：有 / 无
- 配置清单：<项 / 前后语义 / 消费服务 / 默认值 / 受影响环境>
- 权威文档：<路径或链接>；逐项同步状态：<已同步 / 缺 X / 未确认>
- 需要用户补录或确认：<列表>

### 结构合理的部分
简要指出做得对的地方，让作者知道哪些不用改。

### 需要作者说明
评审无法判断意图、需作者解释的设计选择。
```

Finding 必须带：优先级（`P1` 规则分叉 / 状态错误 / 配置漏发 / 该阻断合并；`P2` 重要可维护性问题）、1–10 置信度、精确文件行号、具体代码证据和受影响调用路径、当前结构如何增加变更放大或理解成本、可执行的收敛建议（指明规则归属、语义所有者、保留的副作用边界、该删的低价值包装）。

涉及入参修改的 finding 必须点名：被改的具体字段、下游谁读它、哪段计算可以纯化、哪些副作用必须留在边界。

同一根因的多个症状合并成一条。不说「建议重构」「抽个 helper」「补注释」这种空话。满足标准就明确说没有结构 finding，不为了填模板造问题。

配置发布 finding 以引入或改变配置契约的代码行为证据，列出缺失项、受影响环境和服务。文档访问不到只能报「发布依赖状态未确认」，不能把未知写成缺失。

## 边界

- **只评结构**。功能 bug、边界情况、安全漏洞交给 code review / security review；覆盖率交给测试评审。
- 风格偏好不提意见。项目既有风格与个人偏好冲突时，以项目为准。
- 不建议重命名已发布的 API 字段 / DB 列 / proto field，除非本次就是在改它们。
- 不扩大范围。既有结构问题只在本次改动使其恶化时才提，并标注「既有问题，本次加剧」。
- 一轮内报完，不分批挤牙膏。
- 独立判断，不因为代码是 AI 写的就放松或加严标准。
