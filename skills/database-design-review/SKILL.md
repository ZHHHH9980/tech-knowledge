# 数据库设计评审

从业务事实与生命周期判断表结构是否准确，再用键、关系和范式检查一致性。给出可定位、可执行的建议；不要把“重复值多”“表少”“字段少”当成质量标准。

## 范围与证据

- 默认只读；用户要求评审不等于授权改表、执行 SQL、连接生产数据库或发布 migration。
- 优先读用户提供的业务规则、ERD、字段说明和 DDL；仅在判断关联或数据写入语义需要时读取相关实现。
- 区分逻辑模型、DDL 的实际约束与应用保证。只有设计说明时，明确实现未验证。
- 不从字段名猜测实体、唯一性或关系。缺少关键业务事实时列出待确认问题，仍完成能判断的部分。
- 出现快照、重复明细、多个候选键或 JSON 集合时，按需读 [判断案例](references/judgment-cases.md)。
- 单独评审数据库模型时，本 skill 主导，不额外要求无关的 Figma、接口或性能材料。综合技术方案评审中，用本 skill 完成数据建模部分，合并并去重 Findings，按项目或主报告的优先级口径输出。

## 1. 先确定一行代表什么

为每张表用一句话描述记录粒度，例如“一行代表一笔订单的一条明细”。记录它的实体或关系、生命周期、候选键和主要读写用途。

从需求、输入和预期输出反查模型：是否能表达必须保存的事实，能否回答业务问题？范式正确不能证明需求完整。

对疑似冗余字段，先从需求、明确的业务说明或已确认契约中确定其含义、产生时点、变更规则和保留要求，再检查实现。值相同或代码里存在计算公式，不能单独证明它们是同一业务事实；业务语义缺失时列为待确认，不直接建议删列或拆表。

检查数据属于哪个主体：同一个客户、商品或供应商的当前属性，是否被复制到多处并要求同步修改？分别推演：

- 新建主体时，是否必须捏造另一主体的记录才能保存？
- 更新一个事实时，是否要修改多个位置，漏改后会出现矛盾？
- 删除一条记录时，是否意外丢失仍应保留的另一主体事实？

以这些插入、更新、删除异常说明拆表理由。状态、日期或数量取值相同，不能单凭重复频率抽成新实体；目标是保持业务事实一致，不是“压缩信息熵”。

## 2. 审查键与完整性约束

- 列出业务上的候选键，即能够最小且唯一识别记录的字段组合，再判断选定 PK 是否唯一、非空、稳定。
- 自增 ID 或 UUID 不会自动防止业务重复；按业务唯一性核对相应 `UNIQUE` 约束及其作用范围。
- 联合键逐项解释组成理由，不添加无关字段凑唯一；选自然键或代理键要结合可变性与引用成本，不机械要求某一种。
- 每个逻辑引用明确目标表、目标候选键、是否可空、是否允许孤儿，以及删除和更新语义。
- 物理 FK 必须指向目标数据库允许引用的唯一键；检查类型兼容性与实际约束，`xxx_id` 字段本身不保证参照完整性。
- `NOT NULL`、`UNIQUE`、`CHECK` 和 FK 分别承担必填、唯一、取值和引用约束，互相不能替代；NULL、软删除下的唯一性按数据库与业务语义判断。
- 跨库、跨服务或异步引用可能无法使用物理 FK；检查已有的完整性保证和修复责任，不机械添加 FK，也不自动接受无约束引用。
- 删除策略必须符合生命周期；不要默认选择 `CASCADE`。仅有 FK 也不能证明所有业务必需关系均已存在。

约束语义依据 [PostgreSQL Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html)；评审其他数据库时核对对应产品的实际行为。

## 3. 从两个方向确认关系

同时确认最小基数（是否可选）和最大基数（至多一个或多个），再判断表结构与约束能否表达。

| 业务关系 | 重点检查 |
| --- | --- |
| 一对多 | 引用通常放在多的一侧；可空性是否允许没有父记录；避免误加唯一约束变成一对一 |
| 一对一 | FK 本身只限制引用有效；还需唯一性限制“至多一个”，并确认拆表确有生命周期或职责原因 |
| 多对多 | 用关联表表达，两侧各与关联表形成一对多；业务关系仍然是多对多 |

关联表承载关系本身的属性，如数量、加入时间和角色。唯一性按记录粒度决定：同一对实体只能关联一次时使用组合唯一；允许多次发生时，用事件或明细标识区分，不能无条件套 `UNIQUE(left_id, right_id)`。

## 4. 应用第一至第三范式

先明确业务依赖，再判断范式；字段名、少量样例值或单列代理 PK 不能替代依赖分析。

| 范式 | 评审动作 |
| --- | --- |
| 1NF | 检查一个字段是否混装需要独立操作的多项事实，以及 `product_id1/name1/product_id2/name2` 这类可变数量的重复组；考虑以子表或关联表的多行表达 |
| 2NF | 在满足 1NF 后，检查非键属性是否完整依赖每个候选键；联合候选键的一部分能单独决定的属性，应审查其实体归属 |
| 3NF | 在满足 2NF 后，检查非键属性是否通过另一个非键属性间接依赖候选键；把其他主体的属性放回其所属实体 |

“非键属性”指不属于任何候选键的属性。存在多个候选键时全部检查，不只检查选定 PK；复杂依赖需明确列出，不能靠口诀断言。

以 `A → B` 记录“业务规定同一个 A 只能对应一个 B”的函数依赖，并给出当前表中相应的异常。高阶范式仅在具体依赖问题需要时继续分析。

以上检查参考 [Database design basics](https://support.microsoft.com/en-us/access/database-design-basics) 与 [微软规范化说明](https://learn.microsoft.com/en-us/troubleshoot/microsoft-365-apps/access/database-normalization-description)。

## 5. 审查计算字段、快照与有意保留的数据

- 默认保存原始业务事实；能够从已保存输入按确定规则可靠推导的结果，优先在查询或使用时计算，避免同时维护输入与结果造成不一致。“原子”按业务操作需要判断，不要求无限拆细字段。
- 对每个计算字段确认：输入来自哪里，公式及舍入规则是什么，输入变化后谁更新结果，为什么需要持久化。仅为方便读取而存储、却没有同步保证的结果，应指出具体的失效路径。
- 例如 `subtotal`：如果业务定义为当前明细金额的可重算汇总，默认查询时计算；如果代表提交或结算时确认的金额，则按历史事实或快照评审。不能只因代码能写出 `SUM(...)` 就建议删除。
- 当前主体属性、交易时快照和可重建投影分别判断。订单成交价或当时名称可能是独立历史事实，不应改成始终读取商品当前值。
- 商品名称要先确认语义：如果订单字段只是重复保存商品当前名称，原则上由商品表维护，订单通过商品引用读取；如果保存下单时的名称，商品改名后订单仍需保留旧名称，则属于快照事实。不能仅凭字段叫 `product_name` 判定冗余。
- 历史结算、审计要求或有依据的查询成本可支持保存计算结果；检查计算时点、规则版本、更新所有者、重算方式和允许的一致性差异。不能按当前规则重建的历史结果，先确认事实是否完整，不直接删除；性能理由缺少证据时标记待验证。
- JSON、数组或自由文本是否需要拆分，取决于是否要独立检索、约束、更新及建立关系；不能看到容器类型就认定设计错误。
- 表中大量空列可作为实体边界或子类型的检查信号；先确认字段是否属于同一主体，避免机械拆成大量一对一表。

这些是工程判断边界，应结合项目事实论证，不将 Access 的操作方式直接转成所有数据库的硬规则。

## 6. 用具体操作检验建议

为发现的问题构造最小反例，覆盖适用的新增、属性修改、重复写入、关系增减和删除情形。关联表建议还需核对同一实体对能否重复出现；快照建议需核对主体变化后历史是否保持原值；计算字段建议需核对输入修改后结果是否正确，以及历史计算规则变化是否会错误地重写旧结果。

迁移已有模型时，说明建议涉及的去重、回填和约束验证前提。需要数据查询时给出只读核验方法；执行仍遵循当前授权，不把抽样未发现问题当作已证明唯一性或完整性。

## 输出

结论为“可以接受 / 有条件接受 / 必须修改后再评审 / 证据不足”，并说明已检查的范围和关键限制。

按表给出紧凑覆盖表：`记录粒度 | 候选键/PK | 关系与约束 | 范式/异常 | 有意保留的数据 | 结论`。关系复杂时补充关系表，不重复输出相同证据。

每条 Finding 必须包含：

1. 精确证据位置：DDL/代码 `path:line`，或 ERD、设计文档的明确章节；材料直接贴在聊天中时，用题设编号、SQL 语句或字段及相关业务原句定位，不虚构文件路径。
2. 受影响的业务依赖及违反的契约；不要只写“违反 3NF”。
3. 最小触发例子与数据后果。
4. 最小改动建议及所需 PK、唯一性、FK 或生命周期约束。
5. 验证方法，以及仍待确认的前提。

按实际影响排序：P0 为已证实的关键数据丢失或破坏，P1 为重要的一致性或建模错误，P2 为较低影响的结构问题。范式不符合本身不自动构成高优先级问题。

正常设计放覆盖表，缺少依据的风险放待确认问题。无问题时明确写“未发现需要修改的问题”，不为填满报告制造 Finding。
