# 数据库设计判断案例

以下为评审方法的自拟示例，用于区分模型错误与合理例外；字段名不能代替实际业务规则。

## 重复值与重复事实

假设业务规定某组织的当前联系地址由该组织统一维护：

```text
members(member_id, org_id, org_name, org_address)
```

`org_id → org_name, org_address`。同一组织的地址在多名成员记录中重复，修改可能遗漏；没有成员时也无法独立保存组织。可评估 `organizations` 与 `members.org_id` 的分离。

多名成员具有相同 `status` 则不能推出它是另一个实体。只有状态本身有需要维护的属性、关系或生命周期时，才进一步评估独立表。

## 1NF：用行承载可变数量

```text
surveys(survey_id, question_id1, answer1, question_id2, answer2)
```

如果问题数量可变，第三道题不应要求追加一组列。可用 `survey_answers(survey_id, question_id, answer)` 表示答题关系，并按业务规则约束同一问题是否只能答一次。

`billing_address` 与 `shipping_address` 若分别代表两个固定业务角色，不能仅因字段类型相同就当成重复组。

## 2NF：不能靠加 ID 修复

```text
subscriptions(member_id, publication_id, member_email, started_at)
候选键：(member_id, publication_id)
业务依赖：member_id → member_email
```

会员当前邮箱属于会员，非整条订阅关系；修改邮箱可能漏改其他订阅。把它放回会员实体。增加单列 `subscription_id` 不会消除这项依赖。

若邮箱表示订阅创建时的通知地址快照，则需要重新确认历史语义，不能沿用“当前邮箱”的依赖。

## 3NF：沿依赖找属性归属

```text
devices(device_id, model_id, model_name)
业务依赖：device_id → model_id，model_id → model_name
```

型号当前名称属于型号；逐台设备保存它会形成传递依赖及更新异常。可评估 `models(model_id, model_name)`，由设备引用型号。

不要把示例推广成“所有名字必须独立表”：没有独立身份、关系或维护规则的文本，不需要为了重复出现而拆表。

## 多对多：先确认关联记录的身份

成员可加入多个小组，小组也有多个成员，且同一成员在同组只能有一份当前成员关系：

```text
group_memberships(member_id, group_id, role)
UNIQUE(member_id, group_id)
```

若记录的是历次加入事件，同一实体对可能多次出现。事件 ID、时间和允许重入的规则需要另行定义，不能保留上述组合唯一就认为模型完整。

同理，一笔订单中允许同一商品分成不同批次或不同价格的明细时，`(order_id, product_id)` 未必是候选键；应以明细身份判断。

## 历史快照与派生值

### subtotal：先确认业务定义

同名字段可能有不同含义。若购物车 `subtotal` 是当前条目的金额合计，条目变化时它应随之变化，默认从当前条目计算；若订单 `subtotal` 是提交时确认的金额，后续商品价格、购物车或计价规则变化不应改变它，应按当时的业务事实评审保存方式。

评审先确认金额口径、计算时点、是否冻结、是否允许调整以及历史还原要求，再决定计算或持久化。只看到 `SUM(line_total)`，只能说明实现中存在汇总，不能证明删字段仍满足业务需求。

### 明细金额与快照

商品名称的两种业务定义会得出不同结论：

- **商品当前名称**：业务要求订单展示名称始终跟随商品改名。名称由商品表维护，订单通过 `product_id` 读取；订单再存一份当前名称会增加同步责任，除非有明确的投影或性能理由及维护机制。
- **下单时商品名称**：业务要求历史订单展示用户下单时看到的名称。它属于订单明细的历史事实，商品改名后仍保留旧值，可用 `product_name_at_order` 等命名说明语义。

字段叫 `product_name` 不能告诉评审者是哪一种。先核对需求、字段说明、已确认契约与改名后的预期行为；无法确认时提出问题，不直接建议删除。

`receipt_lines(item_id, item_label_at_sale, unit_price_at_sale, quantity)` 中，成交时名称和单价由交易确定。物品后来改名或调价，不应重写旧收据。

如果 `line_total` 只由已保存的 `unit_price_at_sale × quantity` 按固定规则得到，默认在查询或使用时计算。若三者都存储，修改数量却漏改总额就会产生矛盾；评审需检查所有适用写入路径的同步保证。

若总额还包含交易时折扣、舍入、税费或人工调整，先确认相应输入与规则是否完整保存，以及总额是否代表最终结算事实。不能拿当前价格或当前计价规则重算历史。因查询成本保存汇总时，需说明依据、更新或刷新责任，以及允许的延迟和重建方法。

快照、当前属性副本和缓存投影具有不同的更新责任，评审时分别说明。

## JSON：先看操作需求

一个整体读取的扩展属性文档，与需要逐个删除、去重、查找并校验目标存在的关联 ID 集合，具有不同建模需求。前者可评估 JSON；后者应重点评估关联表。

看到 JSON 只说明需要理解结构与操作，不足以直接报告违反范式。
