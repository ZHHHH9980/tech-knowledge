# 付费调用上游服务：冻结 → 核销 / 解冻状态机

## 场景

用户消耗积分或余额，触发对上游服务的调用（TTS、图片/视频生成、LLM 等）。上游调用耗时长、可能失败，结果也不确定。

## 问题

先扣费、再调用上游，或者调用前直接扣款：

- 上游失败、超时、服务进程被杀时，用户已经付了钱却拿不到结果，引发客诉。
- 事后补偿依赖一条额外的退款链路，链路本身也可能失败，出现漏退或重复退款。

## 正确做法：两阶段扣费

1. **冻结（freeze）**：调用前先冻结本次需要的额度。冻结后余额不可用，但钱还没有扣走。冻结时必须设置过期时间，作为兜底。
2. **调用上游**。
3. **核销（capture）**：上游成功后，把冻结的额度真正扣掉。
4. **解冻（release）**：上游明确失败时，解除冻结，额度退回给用户。
5. **过期兜底**：服务崩溃、核销和解冻都没有执行时，冻结到期后由账务系统自动解冻。

## 状态机

```text
            ┌──────── 上游成功 ────────► captured（已扣费，终态）
frozen ─────┤
            ├──────── 上游失败 ────────► released（已退回，终态）
            └──────── 冻结过期 ────────► expired（自动退回，终态）
```

要点：

- **每一步都要幂等**：冻结、核销、解冻都带同一个幂等键，重试不会重复扣费或重复退款。
- **终态不可逆**：已核销的不能再解冻，已解冻或已过期的不能再核销。冻结已经失效时，核销应作为终态处理（判定生成失败），不能无限重试。
- **扣费状态与业务结果绑定**：只有业务结果已经持久化，才允许核销，避免"钱扣了、结果丢了"。
- **区分是否已扣费**：未扣费的失败允许用户直接重试；已扣费的失败要走明确的补偿或重试规则。

## 教训

- 涉及支付消费的功能，先设计核销状态机，再写调用链路。不要先扣费，因为上游调用不一定成功。
- 状态机里每一个"可能失败"的步骤，都要回答两个问题：失败后积分去哪了？由谁来推进到终态？
- 状态机的实现要接入现有的异步任务框架时，同样要检查共用查询的执行计划（见[《共用高频 SQL 加 OR 导致部分索引不再适用、执行计划退化》](https://github.com/ZHHHH9980/tech-knowledge/blob/main/database/postgres-partial-index-or-predicate-plan-regression.md)）。业务设计正确，不代表实现可以安全上线。
