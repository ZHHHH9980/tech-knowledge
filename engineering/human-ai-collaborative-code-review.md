# 人与 AI 协作 Code Review：从业务路径到可验证的证据

## 现象

AI 写出的代码可以实现需求，但人 review 时仍容易遇到两个极端：只听 AI 解释就接受正确性，或者逐行追问、不断跳入 interface 和基础封装，最后丢失最初的问题。

通用检查清单有帮助，却不能替代代码阅读能力。真正需要训练的是：快速建立业务规则、数据状态与实际实现之间的映射，知道哪里需要证据、哪里可以停止。

本文整理一套人与 AI 协作的方法。抽奖例子是教学化场景，用于解释推理方式，不代表对任何具体线上实现的完整审计结论。

## 根因

- 没有整体路径图时，局部函数看懂了，也可能不知道它在保护什么。
- 函数名、注释和 AI 的流畅解释表达的是意图，不等于实际机制已经成立。
- 每个函数都机械套完整流程，会让 review 成本失控。
- 功能正确与设计合理是两个问题：能跑通不能证明每张表、每个抽象都必要；表少也不能证明简单。

## 方法：先建立地图，再围绕风险取证

### 1. 画出业务执行路径与数据流

先用一句话明确需求，再浏览入口和主流程，画出粗略实现路径。图中标出关键状态、事务边界、锁和外部副作用；需求仍是判断实现的依据，不能拿现有实现反过来定义需求。

以抽奖为例：

~~~text
请求进入
 → 查旧订单：存在则重放
 → 开启事务
     → 占订单：重复则重放
     → 锁用户进度、读取配置
     → 算价格、检查涨价与余额
     → 锁全局计数和库存
     → 逐抽选奖、检查资格、更新内存状态
     → 扣票
     → 写回订单、结果、库存、计数
 → 提交；出错则回滚
 → 返回结果
~~~

在路径上标出必须成立的 invariant（不变量），例如：

- 同一用户、同一活动、同一请求号至多产生一次有效结算。
- 订单、扣票、库存和进度一起成功或一起回滚。
- 有限库存不能超卖。
- 实扣金额与订单结算金额一致，并符合用户确认价格的约定。
- 每抽按正确的用户抽次进入奖池，保底计数与实际结果一致。

“加了锁”“用了循环”是候选实现机制；“库存不能超卖”“十连抽依次推进抽次”才是业务要求。

### 2. 简短识别变更范围

标记 DB、API、事务、并发、缓存、MQ、权限、版本兼容等受影响部分，决定检查重点。新需求也会接入已有账户、部署和数据体系，并不天然没有兼容风险。

这一步通常只需几句话。区分本次新增或改动的机制与已验证且未变化的基础设施，不必每次重新审计整个系统。

### 3. 构造具体失败场景

不要只问“有没有并发问题”，要给出参与者、时序和预期结果。

| 维度 | 抽奖场景 | 要验证的结果 |
| --- | --- | --- |
| 边界 | 余额刚好够、保底差一次 | 金额与规则边界正确 |
| 重复 | 提交成功但响应丢失，随后重试 | 返回同一结算，不重复扣票 |
| 并发 | 同一请求重试时，首笔事务仍未结束 | 至多一笔有效结算 |
| 资源竞争 | 不同订单争抢最后一份库存 | 不超卖，失败或空奖符合产品约定 |
| 中途失败 | 扣票后写结果失败 | 所有关联写入回滚 |
| 兼容 | 旧页面提交旧价格或缺失字段 | 按契约接受或明确拒绝 |
| 容量 | 同活动请求增加、历史记录增长 | 找出锁等待与查询增长点，再测量 |

失败场景不只是阅读各种 err 分支；它还包括没有返回错误却违反业务约定的情况。

### 4. 挑战设计是否必要

针对刚才的场景追问：数据是谁拥有的？为什么需要这个字段、表或抽象？删除后由什么机制接替？是否只是为尚不存在的需求增加维护负担？

设计讨论应产生可比较的方案和成本，而不是停在“我觉得复杂”。数据库设计的例子见后文。

### 5. 带着问题查代码，形成证据链

每次只保留一个明确问题，沿相关调用和数据流验证。遇到 interface 时，让 AI 定位实际注入的实现及接线位置，不要列出所有同名函数。

| 结论 | 需要的证据 | 不能单独作为证明的东西 |
| --- | --- | --- |
| 请求幂等 | 唯一约束、占单冲突处理、重复分支在结算前退出 | 先查询旧订单 |
| 全部回滚 | 相关仓储绑定同一事务、错误传播、提交与回滚实现 | 函数叫 InTransaction |
| 库存不超卖 | 加锁读取，锁覆盖计算与写回、库存检查、所有写入路径遵守协议 | 内存里执行减一 |
| 不多扣票 | 报价校验、结算金额传递、扣票命令和订单写回使用同一金额 | 有 CheckBalance 调用 |

将结论标为“已验证”“推断”“待验证”。记录版本和关键位置，避免 AI 换一轮回答后把推测升级成事实。

### 6. 最后看代码品味

命名、职责、封装、重复、函数长度和注释放在正确性之后。如果结构已经让事务或状态所有权无法辨认，它就是影响正确性审查的实际问题，应该提前处理。

## 三个贯穿案例

### 幂等：查询只是快速路径

事务外查询旧订单，可以快速处理已经完成的请求；两个重叠请求仍可能都查不到。

以 PostgreSQL 的唯一约束与 INSERT … ON CONFLICT DO NOTHING 为例，冲突可能涉及尚未结束的事务，此时插入可能等待对方结束。必须核实真正的唯一键，例如 (campaign_id, user_id, client_request_id)，以及提交、回滚、冲突后读取的分支和隔离级别假设。不能只凭语句名称就宣称所有情况都正确。

如果只有成功占单的请求能进入扣票，并且占单、扣票和结果写回都处于同一事务，订单幂等可以保护这条路径内的扣票不重复。扣票是否还需要独立幂等，取决于它是否存在独立入口、事务外调用或其他重试路径，不应机械叠加保护层。

### 事务：看对象绑定与错误传播

主流程里的事务回调只能说明意图。需要继续确认传入的抽奖仓储与票务仓储都使用同一个事务对象，后续方法没有退回普通连接，错误能向外返回。

同一数据库事务不能自动回滚外部 HTTP 调用或已经发送的消息；路径存在这类副作用时，需要另看它的交付和恢复机制。

证据链闭合后可以停止，不必每次重新阅读数据库驱动。

### 库存：正确性与性能分别判断

FOR UPDATE 是行级锁定机制。需要看查询究竟锁中了哪些行、锁持有多久，以及库存检查和写回是否都在保护范围内。

如果每次抽奖都锁住活动的全部奖品，或者更早就锁住同一个全局计数行，同活动请求可能被串行化。这是性能审查的切入点，但不能仅凭“有锁”判定性能不达标；还需结合事务耗时、目标吞吐和锁等待测量。

## 数据模型：不以表的数量评判设计

先给每张表写一句话：“一行代表什么？”再问事实来源、生命周期、约束与查询方式。

| 对象 | 典型含义 | 合并或删除前要回答的问题 |
| --- | --- | --- |
| order | 一次请求或交易，可包含多抽 | 请求号、总价、配置版本放哪里？如何保证请求级唯一与重放？ |
| result | 一次抽取的结果 | 十抽共享订单号没有问题，但交易级事实是否要在十行重复？约束如何表达？ |
| progress | 用户抽次与保底状态 | 能否从历史准确重算？规则重置与版本变更是否保留足够历史？每次扫描成本和并发保护如何解决？ |
| QA rule | 测试指令及其消费状态 | 是活动级单值还是用户级多条？生命周期、权限和清理是否与控制表一致？ |
| backpack | 用户当前可持有或使用的奖品 | 只是非空中奖记录的展示，还是还有领取、消耗、转移和撤销？ |

订单数量不等于抽数：一次订单可能包含十抽。结果条数也只有在每抽都有记录、统计范围和 QA 等口径一致时，才可能作为抽数来源。

如果背包只是结果列表，可以先用查询或视图表达；如果具有独立状态变化，就需要明确保存那些不能从中奖历史直接推导的事实。

可重算状态也可以持久化，但必须说明它解决什么查询或并发问题、如何与事实同步、如何校验或重建。它不是因为“能算出来”就必须删，也不是因为“以后可能快”就必须加。

单活动系统可以不做通用活动框架。是否保留 campaign_id，要结合当前活动归属、幂等范围与数据隔离判断。约定“空值永远表示第一场活动”同样是一条长期规则，未来迁移需要清晰回填和兼容计划，并非天然比显式标识更简单。

每个删表或加表提议都写清：当前解决的问题、替代实现、查询与写入成本、约束变化、迁移成本。没有明确收益时，不为追求表数更少重写已经合理的设计。

## 人与 AI 如何分工

人负责确认业务规则、选择风险重点、判断设计取舍，并读懂关键路径。AI 负责整理路径图、定位实现和约束、提出具体反例、收集证据。

不要求每一步都问 AI。把同一风险相关的代码和问题一次交齐，要求它返回：

~~~text
问题／不变量：
具体失败时序：
实际保护机制：
证据位置与代码版本：
结论：已验证／推断／待验证
剩余缺口与下一处最小检查点：
~~~

可复用提问：

> 先画入口到持久化的主路径，标出状态、事务、锁和外部副作用。针对这次变更列出最多五个高风险不变量，每个给一个具体反例。逐项定位实际实现与约束，区分已验证、推断和缺失证据。不要只总结 diff，不要按每个函数重跑整套流程；问题已经闭合就停止，设计建议说明当前收益和替代成本。

第二个模型的赞同也不是证据。对模型表现波动的应对，是让结论可追溯、可复查，而不是增加更多没有依据的解释。

## 模式抽象与停止条件

整项需求先做一次路径图和范围判断；随后以“一个业务保证或风险场景”为单位循环执行第 3、4、5 步，最后看代码品味。

当业务约定清晰、反例有保护机制、关键证据已核实、剩余未知已明确时，停止向下钻。确认过且未改变的基础封装可以按契约复用；契约变化、证据矛盾或发现新入口时再展开。

一次 review 的最小产物是：路径图、重点不变量、风险与证据表、必须处理的问题以及明确保留的设计取舍。目标是降低遗漏与理解成本，不是证明系统永远没有 bug。
