# 人与 AI 协作 Code Review：先看全貌，再追关键问题

AI 写完代码以后，人应该怎么看？逐行让 AI 解释，容易变成一场很长的代码导读；直接接受它的总结，又不知道结论是否可靠。

比较实用的做法是：先理解整个功能怎么运转，再挑出最不能出错的地方，带着具体问题看代码。AI 帮忙找路和收集依据，人负责判断规则是否正确、方案是否值得。

## 1. 先画出整体流程

先说清楚这次要解决什么问题，再看入口和主流程，画一张简单的图。几行文字就够，不需要先研究每个函数。

~~~text
用户操作
 → 检查输入和权限
 → 读取需要的数据
 → 按规则处理
 → 保存变化
 → 返回结果或更新页面
~~~

按实际功能补上分支：失败在哪里返回？哪些步骤需要一起成功？有没有调用其他服务？前端收到结果后又做了什么？

看图时要能回答三个问题：**数据从哪里来，经过哪些变化，最后存到哪里、展示给谁。** 有了这张图，之后跳进某个函数时，才知道自己在看哪一段。

接着写下三到五条“无论怎么操作都必须成立的规则”。这就是常说的 invariant（不变量），例如：

- 用户只能修改自己有权限修改的数据。
- 同一次操作重复提交，不能产生两次不该重复的结果。
- 页面显示保存成功时，数据确实已经保存。
- 用户看到的金额与最终收取的金额符合约定。

“用了锁”“放进事务”是实现办法；“不能重复处理”“不能只保存一半”才是要保证的结果。

## 2. 看这次改动碰到了哪里

沿着流程标出新增和修改的部分，决定哪里值得多看。

| 改动位置 | 顺手追问 |
| --- | --- |
| 页面和交互 | 加载中、失败、重复点击时，用户看到什么？ |
| 接口和权限 | 谁能调用？旧页面还能用吗？ |
| 数据和存储 | 多了一份什么数据？谁负责更新？ |
| 多人共享的资源 | 两个人同时操作，会互相覆盖吗？ |
| 后台任务或外部服务 | 超时后怎么办？重试会不会重复执行？ |

这一步通常几句话就够。小改动缩小检查范围，大改动再展开；不用每次审查整个系统。

## 3. 想几个“不顺利”的场景

正常流程能跑通，只回答了一部分问题。换几个条件，看看原先的规则还能不能成立。

| 角度 | 可以直接问的问题 |
| --- | --- |
| 边界 | 没数据、只有一条、刚好达到上限，会怎样？ |
| 重复 | 用户点了两次，或者网络超时后重试，会怎样？ |
| 同时发生 | 两个人同时修改同一条记录，会怎样？ |
| 做到一半失败 | 前一步成功，后一步失败，最终留下什么？ |
| 新旧版本 | 页面还没更新，服务已经更新，能配合吗？ |
| 数据增长 | 数据多十倍，是否仍然全部查出、全部计算？ |

不需要每次把所有格子填满。根据第 2 步，挑最相关的几个场景。

让 AI 给出具体过程，比如“先发生 A，随后 B，最后出现了什么错误”，比问一句“有没有问题”更容易检验。没有报错也可能有问题，例如旧请求的结果覆盖了新请求的结果。

## 4. 问一句：有必要这样设计吗？

功能正确以后，还要看实现是否让后续维护变难。

- 新增的字段、表或中间层，解决了什么当前问题？
- 同一份信息存了两处，谁负责保持一致？
- 这个规则由哪里负责，为什么散落在多个地方？
- 如果删掉这一层，逻辑会更清楚，还是只是搬到了别处？
- 是现在确实需要，还是在为一个尚未确定的未来需求做准备？

例如“是否需要再建一张表”，可以先问：**一行代表什么？谁写、谁读？不建这张表以后，查询和更新要怎么做？**

表少、文件少，不一定更简单；分得细，也不一定职责更清晰。比较的是理解、修改和保证正确性的总成本。提出简化建议时，要能说明具体省掉了什么、又增加了什么。

## 5. 带着问题看代码，找到依据

前面的讨论会形成一些待验证的判断。此时再进入相关代码，确认它们是不是真的成立。

例如要检查“重复提交不会重复处理”：

~~~text
提出问题：用户快速点两次，会执行两遍吗？
 → 找到入口：两次请求分别走哪里？
 → 找到保护：靠什么识别和拦住重复操作？
 → 检查遗漏：两次同时到达时，这个办法还成立吗？
 → 记录结论：已经确认，还是缺少哪一处依据？
~~~

如果只看到“先检查有没有，再执行”，还不能直接确认安全：两个请求可能都先查到“没有”。需要继续找到实际处理竞争的地方。

但也不必因此把所有底层代码读一遍。每次进入下一层之前，先说清楚：**我现在要确认的具体问题是什么？**

遇到接口定义、层层封装时，可以让 AI 一次找出“这条路径实际用了哪个实现、在哪里接上的、关键代码在哪”。函数名和注释可以帮助定位，不能单独证明行为正确。

让 AI 的回答区分三种情况：

- **已确认**：相关代码或验证结果支持这个结论。
- **推测**：看起来如此，但还依赖没有检查过的条件。
- **待确认**：材料不够，需要继续查。

关键结论保留代码位置和版本。AI 说得自信、另一个模型也赞同，都不能代替依据。

## 6. 最后看代码是否好读、好改

再检查命名、重复逻辑、函数职责和注释。这些影响维护，但通常应排在行为正确之后。

如果代码已经复杂到无法判断“谁改了数据”“失败后会怎样”，结构问题就正在妨碍正确性检查，应提前处理。

## 实际使用时，不必机械走六遍

**整个需求先做第 1、2 步；每个重要问题结合第 3、4、5 步讨论；最后看第 6 步。**

一个问题可能跨好几个函数；一个简单修改也可能几分钟就看完。检查单位是“一个需要保证的行为”，不用每个函数重新套完整流程。

比如审查保存功能，可以先追“失败后会不会留下半份数据”；这个问题确认完，再看“多人编辑是否互相覆盖”。不要一边追问题，一边不断岔到无关的命名和封装细节。

## 什么时候可以停止深挖？

当你能说清下面三点，就可以结束当前问题：

1. 要保证什么结果。
2. 实现通过什么办法保证，关键依据在哪里。
3. 这个保证有什么前提，还有什么没有确认。

已经验证且本次没变的基础封装，可以在明确前提下信任；发现它被改动、出现新入口，或实际表现与约定不一致时，再继续往下查。

缺少关键依据时，应把问题留下，不能写成“已通过”。停下的理由应该是问题得到了回答，而不是 AI 解释得足够长。

## 人和 AI 怎么配合更省力？

人重点做三件事：理解需求、选择重点、判断取舍。AI 帮忙画流程、定位代码、找反例和整理结论。关键路径仍然需要人能读懂；逐行追问 AI 无法替代这种能力。

不必每一步都问一次。可以把同一个问题涉及的材料一起交给 AI：

> 先用通俗语言画出这次功能的整体流程，标出数据在哪里读取和修改。根据改动挑出最值得检查的几个问题，给出具体出错场景，再定位相关代码验证。区分已确认、推测和待确认。设计建议说明当前收益和代价。不要逐行解释，也不要扩展到与问题无关的底层细节。

最后用一张短表留下结果，方便自己或下一个人接着看：

| 要保证什么 | 可能怎样出错 | 实现与依据 | 结论或待办 |
| --- | --- | --- | --- |
| 填写本次的关键规则 | 写一个具体场景 | 相关代码位置或验证结果 | 已确认／待确认／需要修改 |

这套方法提供的是提问顺序。长期要练习的能力，是把“用户希望发生什么”与“代码实际做了什么”对应起来，并知道哪些差异值得追究。
